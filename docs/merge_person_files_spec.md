# Spec: `tools/sync_person_files.py`

## Purpose

A recurring (run every so often, across decades) sync tool that merges Person data from another structured source into your hand-maintained personal Person files in a hal_md-style Obsidian vault — **updating the personal files in place** — while remembering, across runs, which differences you've already reviewed and accepted or ignored. The tool itself is source-agnostic: it just reconciles two sets of `Person.md`-style files. Today the other set happens to come from a LinkedIn-extraction tool, but nothing in the merge logic is LinkedIn-specific — any other source producing files in the same format would work the same way.

- **Personal set**: Hand-maintained over decades. Richer relationship context — e.g. `reports to [[Name]]`, precise position start/end dates, personal notes. **This is the file that gets updated — but only the specific fields/sections covered by the rules below. Everything else in the file (all other frontmatter, all other sections, formatting, comments, ordering) must be left byte-for-byte untouched.** These files hold a lot more information than what this tool touches, and none of it should be reformatted, reordered, or dropped as a side effect of the merge.
- **Other set**: Machine-generated by an existing extraction tool (currently your LinkedIn extractor). Frontmatter contact/skill fields, a `## Bio` section, and a `## Positions` section with OpenAI-summarized job descriptions.

Both sets follow the `Person.md` template (YAML frontmatter + defined body sections).

## Inputs

- `-e / --existing` — path to the existing Person-file folder (recursive, folder-per-person). **This is modified in place.**
- `-i / --incoming` — path to the incoming Person-file folder (e.g. today, your LinkedIn export folder). Read-only, never modified.
- `-t / --state-dir` — path to the **persistent decision store**, default `C:\data\dev-output\people_sync_state`. This directory lives outside the vault/git repo (personal data, not for GitHub) and is what you back up separately.
- `-c / --config` — optional config JSON (thresholds, field-rule overrides)
- `--editor` — command to launch for the review CLI's Edit action (default: `$EDITOR`/`$VISUAL` env var if set, else `code` if on PATH)
- `-d / --debug` — verbose logging
- `-n / --dry-run` — compute and report what *would* change, write nothing, touch no state
- `-x / --max` — cap number of people processed (for testing on a subset)
- `-g / --tag` — optional; only process personal files whose frontmatter `tags` include the given value (e.g. `--tag alist`). Repeatable/comma-separated for multiple tags. Matching, merging, and file creation are all scoped to this filtered set for the run; everyone else is left completely alone and doesn't even appear in that run's reports.
- `--linkedin-id` — optional; process only the person(s) with this `linkedin_id` value (repeatable for a small handful of specific people). Named after the actual frontmatter field, which today is LinkedIn-specific.
- `-p / --slug` — optional; process only the person(s) with this personal-file `slug` (repeatable). Same use case as `--linkedin-id` — pick whichever identifier you have on hand.
- Either `--linkedin-id` or `--slug` (or both, combined) take precedence over `--tag`/`--max` when given — naming specific people is the whole scope for the run, whether or not they carry the filtered tag.
- `-m / --normalize-positions` — runs the one-time Position description format migration instead of a sync (see below). Independent of `--incoming`; only touches the existing files. Combines with `--dry-run`, `--tag`, `--slug`, `--max` the same way the regular sync does.

Before modifying any personal file, write a backup copy into `--state-dir/backups/<YYYY-MM-DD>/<First Last>.md` — a folder per run date (the date the tool was run, not per-person), containing a copy of each modified person's file named the same way you'd naturally identify them (first name space last name), not by slug.

*(Edge cases to handle: if the tool runs more than once on the same date, later backups in that day's folder would overwrite earlier ones — append a run sequence or time-of-day suffix if that matters to you. Two different people can share the same first+last name — since slugs must always be unique, if a first+last name collision occurs, append the slug in parentheses for the backup filename only, e.g. `John Smith (jsmith-2).md`, purely to keep backup files from overwriting each other; this is a display-only disambiguator, not a sign anything's wrong with the vault.)*

## Persistent decision store (`--state-dir`)

This is the key new piece that makes repeated syncing over decades practical: once you've made a call on something, the tool won't ask again unless the underlying data actually changes.

- `matches.json` — confirmed personal-slug ↔ other-file identity links (by slug, `linkedin_id`, or manually validated name match). Reused on every run so re-matching only happens for people not yet linked. If a previously-linked `linkedin_id` changes, log it as a flag (possible profile recreation) but keep the existing match rather than silently breaking it.
- `field_decisions.json` — per-person, per-field record of conflicts already resolved: the two values compared, the decision (`accepted_other` / `kept_personal`), and a timestamp/hash of the source values. On a later run, if the other file's value for that field is unchanged since the decision, skip it silently. If it changed again, re-flag as a new decision. *(Note: "ignore for now" is deliberately **not** stored here — it's a no-op that just leaves the item in the pending queue for next time; only `accepted_other` and `kept_personal` are permanent.)*
- `sync_history.json` — append-only log of every run: timestamp, files touched, counts, which decisions were newly made vs. reused.

## Matching (unchanged from before, now persisted)

1. **Slug exact match** → confirmed, stored in `matches.json`.
2. **`linkedin_id` exact match** → confirmed. (Not treated as broken if it later changes — see above.)
3. **Name-probability match** (first + last name similarity, corroborating signals) → above a high threshold, auto-confirmed and stored; middle band goes to `manual_review.csv` for you to confirm once, after which it's remembered permanently in `matches.json`.

## Field-by-field merge rules

Each field/section has different risk/confidence, so each gets its own rule rather than one blanket policy. Frontmatter fields and body sections are handled separately below since they're structurally different parts of the file.

### Frontmatter fields

| Field | Rule |
|---|---|
| *(all other frontmatter fields)* | **Never touched.** Only the fields explicitly listed in this table are read or written. Every other frontmatter field on the personal file — anything not named here — is left exactly as-is, same value, same position, same formatting, regardless of what the other file has for it. |
| `last_updated` | **Set only when the tool changes an existing personal file.** After a successful merge or Position normalization writes a file, set this field to that run's date as `YYYY-MM-DD`. Do not update it for dry runs or no-op syncs. |
| `skills` | **Auto-merge, no review.** Union the other file's skills into the personal file's skills list, de-duplicated. Purely additive. |
| `mobile`, `emails`, `linkedin_id` (contact info) | **Careful — never silent-overwrite.** First time a personal vs. other-file value differ for a person, flag in `manual_review.csv`. Your decision (keep personal / accept other / ignore) is recorded in `field_decisions.json` and honored on all future runs as long as the other file's value doesn't change again. |
| `birthday` | **Personal always wins**, never overwritten. Compare only at the shared precision — the other source only ever provides `YYYY-MM` (today, LinkedIn), personal may have `YYYY-MM` or `YYYY-MM-DD`, so compare year+month only. If they disagree at that precision, don't change anything, but note the mismatch in the run's report so you're aware the other source disagrees with your file. |
| `first_name`, `last_name` | Personal wins if present; fill from the other file only if the personal file is missing it. |
| `slug` | Never changed by this tool — personal file's slug is the permanent identity anchor. |

### Body sections

| Section | Rule |
|---|---|
| `## Bio` | **Similarity-gated.** Compare personal vs. other-file bio text similarity (e.g. `difflib.SequenceMatcher` ratio). If ≥ 70% similar, treat as "same bio, refined" and update the personal file to the other file's version. If < 70% similar, treat as separate content worth keeping both — **append** the other file's bio below the existing one, separated by a blank quoted line (i.e. `>` on its own line) so it reads as a distinct block rather than overwriting anything. No manual review needed for this case since nothing is lost either way. |

The `## Positions` and `## Notes`/`## People` rules are detailed just below, since Positions needs more than a one-line rule.

- **`## Positions`**: Match individual entries by (organization + overlapping date range).
  - **Dates**: same precision rule as `birthday`. The other source typically only provides `YYYY-MM`; your personal entries often have `YYYY-MM-DD`. Whichever side has the finer-grained (more precise) date wins for that start/end date — in practice this usually means personal wins since it's more often `YYYY-MM-DD`, but if personal only has `YYYY-MM` (or is missing a date) and the other file has more precision, take that one. Compare at shared precision to detect disagreement; if the values conflict beyond just precision (e.g. different months, not just missing days), flag it in `manual_review.csv` rather than silently picking one.
  - Keep the personal entry's `reports to [[Name]]` line if present — the other file never has this.
  - **Retain existing quoted descriptions and sub-bullets.** If a personal Position entry already has a blockquoted description and/or sub-bullets underneath it, those are preserved as-is — never dropped, replaced, or reformatted. Append the other file's summarized description only if the personal entry doesn't already have one of its own. When appending a new blockquoted description, indent the `>` with exactly two spaces to nest it under the position bullet (e.g. `  > - some description text`), matching the format used elsewhere in this spec.
  - Positions only in the other file (new roles not yet in your personal file) get appended, its formatting (quoted description, etc.) carried over as their own entry.
  - Positions only in personal (older/private/informal roles) are left untouched.
  - **After merging, re-order the full `## Positions` list oldest to newest** by start date, so the final section always reads chronologically regardless of what order entries originally appeared in either source file. Entries with only a `YYYY-MM` start date sort using that month; ties (or missing dates) keep their relative original order.
- **`## Notes`, `## People`, etc.**: personal-only sections, never touched by this tool.

## Reporting (every run, including dry-run)

- `match_report.csv` — match status for everyone processed this run
- `manual_review.csv` — new conflicts needing a one-time decision (bio below threshold, contact-info differences, ambiguous name matches, birthday mismatches for awareness)
- `changes_applied.csv` — for a real (non-dry-run) run: exactly which fields were changed on which personal files, and from what value to what value
- Console summary: people processed, auto-merged fields, new decisions needed, decisions reused from prior runs

## Review CLI

Manual review happens as an interactive terminal session — a colorized, git/GitHub-style diff view right in the console, driven by single-keypress commands. No web server or browser; this runs cleanly under WSL like everything else in the toolchain.

**Launch**: `--review` starts an interactive terminal loop reading from `--state-dir/pending_review.json`.

**Recommended implementation**: Python's `rich` library (or plain ANSI escape codes to avoid the dependency) for colored output, plus single-keypress input (no Enter required) via `readchar` or a raw-mode `termios` read, so `a`/`r`/`i`/`e`/`q` act immediately.

**Per-item display**:
- Header line: person name/slug and field name (e.g. `Jane Doe — mobile`, `Jane Doe — Position: Acme Corp, Senior Engineer`).
- Git-style diff:
  - Short single-value fields (mobile, emails, birthday): `- <old value>` in red, `+ <new value>` in green.
  - Longer text (Position descriptions, or anything else needing a closer look): word-level diff, unchanged words in default color, removed words in red, added words in green — like `git diff --word-diff`, rendered directly with ANSI colors.
- Prompt line: `[a]ccept  [r]eject  [i]gnore  [e]dit  [q]uit`
- Running counter, e.g. `Reviewing 12 of 47 — Contact info`.

**Keys** (same behavior as before, terminal-driven):
- **`a`** Accept — take the other file's value, written to `field_decisions.json` as `accepted_other`, applied on the next sync pass.
- **`r`** Reject — keep personal, written as `kept_personal`, remembered permanently unless the other file's value changes again later.
- **`i`** Ignore for now — no decision recorded, item reappears next `--review` session as if unreviewed.
- **`e`** Edit — opens the person's existing file in the configured editor (`--editor`, default `$EDITOR`/`$VISUAL`, else `code`), which works fine from WSL against files on the Linux or mounted Windows filesystem. Doesn't record a decision by itself; re-checks the field after you save and either clears it (if your edit already resolved it) or leaves it pending for you to mark.
- **`q`** Quit — exits immediately, from anywhere. Every `a`/`r` decision is written to disk the instant it's made, so nothing reviewed is ever lost; relaunching `--review` resumes with only the still-pending items, in the same order.

**Batching a large first-run backlog**: filtering happens via a flag — e.g. `--review --field-type contact_info` to work through one category at a time — or just run through everything in one pass, with `q` available whenever you want to stop.

The `manual_review.csv` export still gets written each run for an at-a-glance/offline summary alongside the interactive session.

## Reconnect report: recent changes with no interaction

A separate output file, `reconnect_with.csv`, generated every run (dry-run or real), flagging people worth reaching out to: anyone with a job change or new education entry in roughly the past year where you haven't logged any interaction with them since.

- **Lookback window**: `-w / --lookback-days` (default `365`) — how far back counts as "recent" for a change.
- **Detecting the change**: after merge, scan the person's final `## Positions` section (jobs and education both live here per the other source's format) for any entry whose start date falls within the lookback window. This is computed from the merged/current file state each run — not just "changes made this run" — so it stays correct even if the position was added in a prior sync and you still haven't reached out. *(Note: the exact way job vs. education entries are distinguished in a Positions entry — e.g. an entry-type field, a separate heading, or keyword detection on the title/degree — should match whatever structure the other source (currently your LinkedIn extraction tool) already writes; confirm the exact entry format before implementing this detection.)*
- **Detecting interaction since the change**: scan the person's `## Notes` section for dated entries in either of the two forms actually used there, and treat both as valid interactions:
  - **Embedded dated-file wikilinks**, e.g. `![[bill-smith/2026-07-11.md]]` — extract the `YYYY-MM-DD` from the filename portion of the link.
  - **Manual inline dated notes**, e.g. `- 2026-03-12: we said hello in the hallway` — extract the leading `YYYY-MM-DD`.
  
  If any extracted date (from either form) falls on or after the change's start date, count it as an interaction and don't flag the person. If none is found, the person has had a life change you haven't followed up on.
- **Output columns**: `slug, name, change_type (job/education), organization_or_institution, title_or_degree, change_date, last_interaction_date (blank if none found), days_since_change`.
- Sorted by `days_since_change` descending (longest-overdue reconnects first) or by `change_date` — pick whichever's more useful once you see real output; this is easy to adjust later.
- This report is purely informational — it never modifies any file, and runs even in `--dry-run` or when scoped by `--tag`/`--slug`/`--linkedin-id`.

## One-time cleanup: Position description format migration

Many existing personal files use an older format for Position descriptions — a fenced code block under the position line:

```
* Title, [[Company]], [[City]], 2023-01-02 to 2025-10-02, reported to [[Bill Smith]]

    ```
    this was the description
    in sub-bullets
    ```
```

Going forward, descriptions should use blockquoted sub-bullets instead:

```
* Title, [[Company]], [[City]], 2023-01-02 to 2025-10-02, reported to [[Bill Smith]]

  > - this was the description
  > - in sub-bullets
```

This migration is **separate from the sync itself** — a one-time cleanup pass, run via its own flag (e.g. `-m / --normalize-positions`), that walks the personal vault independently of any matching/merging against the other source and rewrites old-format description blocks into the new blockquote format wherever it finds them, across every Person file, not just ones touched by a merge this run.

- **Detection**: a fenced code block (```` ``` ````) immediately following a position bullet line, containing the description/sub-bullet lines.
- **Transformation**: remove the fence markers, convert each line inside the block to a blockquoted bullet (`> - <line text>`), preserving the original text and line order exactly — only the wrapping syntax changes. **Indent the `>` with exactly two spaces**, matching the nesting level of the position bullet above it (this is what makes it render as a sub-item of that bullet in Obsidian rather than a top-level blockquote) — e.g. `  > - this was the description`, not `> - this was the description` flush against the margin.
- **Idempotent**: entries already in blockquote format are left untouched; running this twice produces no further changes.
- **Same safety net as the regular sync**: back up each modified file first (same `--state-dir/backups/<YYYY-MM-DD>/<First Last>.md` convention), supports `--dry-run` to preview what would change without writing, and respects `--tag`/`--slug` scoping if you want to test on a subset before running it across the whole vault.
- Only the description-block syntax is touched — the position bullet line itself (title, company, dates, `reported to`), any other bullets, and all other file content are left exactly as they are.

## Scope of files scanned

This tool only ever reads/writes `Person.md`-based files. When walking the personal vault (and the other source's export folder), skip:

- **Dated interaction files** (`YYYY-MM-DD.md`), consistent with the skip rule already used in `update_interests.py`.
- **`media/` subfolders** and everything inside them (images, attachments, etc.) — never traversed, read, or backed up as part of this tool's operation.

Only the person's own `<First Last>.md` file — never named by slug — counts as a Person file for matching, merging, backup, and reporting purposes.

## Edge cases

- Person in personal set only → untouched, noted in report.
- Person in the other set only → **auto-created** as a new personal Person file (see "Creating new personal files" below), noted in report as `other-only, created`.
- Duplicate `slug` found anywhere in the personal vault (two different files claiming the same slug) → this must never happen — `slug` is the permanent identity anchor everything else in this spec depends on. Treat it as a **per-person skip, not a whole-run halt**: skip processing for those specific conflicting people only, log the conflict (both file paths) to a top-level `slug_conflicts.csv`/console error, and leave their files untouched until the conflict is resolved by hand outside this tool. Everyone else in the vault is processed normally. Same treatment for a duplicate slug found within the other set.
- Malformed/missing frontmatter → skip that file, log clearly, never crash the batch.
- State-dir missing/first run → initialize empty store, treat everything as new.

## Creating new personal files (other-set-only people)

When a person from the other set has no match in the personal set after the full matching pass:

- Generate a `slug` using the same convention as the rest of hal_md (not just reused from the other file's own slug, since it may not follow your rules).
- Create the standard **folder-per-person** structure under `--existing`: `<slug>/` containing the new `<First Last>.md` Person file (never named by slug) plus an empty `media/` subfolder, matching the layout of every other person in the vault.
- Populate the new file from the other file's data as-is: frontmatter (`first_name`, `last_name`, `mobile`, `emails`, `linkedin_id`, `skills`, etc.), `## Bio`, and `## Positions` — there's no personal version to reconcile against, so no conflict logic applies here; it's a straight copy into the template structure.
- Record the new person in `matches.json` immediately (personal slug ↔ other-file identity) so subsequent runs treat them as an existing matched pair, not a new creation.
- List every newly created person in `changes_applied.csv` (e.g. `action: created_file`) so a first run against a large export from the other source doesn't silently add dozens of files without a clear record.

## Non-goals (v1)

- Re-running OpenAI summarization on merged Position text.
- Deduping people who exist twice *within* the same set (separate pass, same pattern as the existing `organizations.json` dedup work).

## Conventions to follow (matching existing hal_md scripts)

- **Surgical edits only.** Never rewrite a personal file wholesale. Parse frontmatter and body sections, change only the specific fields/entries this spec covers, and write back preserving everything else exactly as it was — key order, spacing, comments, unrelated sections, wikilink formatting. If the parsing library used would normally reformat untouched YAML/Markdown on write, guard against that (e.g. diff the output against the original for any lines outside the touched fields, and fail loudly rather than silently reformatting). *(The one deliberate exception is the `## Positions` list itself, which is intentionally re-ordered oldest-to-newest as part of the merge — see the Positions rules above; nothing else in the file should shift.)*
- Standalone script, `-e/--existing`, `-i/--incoming`, `-c/--config`, `-d/--debug`, `-n/--dry-run` flag conventions.
- `---`-delimited YAML frontmatter parsing consistent with other hal_md tools.
- MIT license; disclaimer that it modifies personal files in place and to keep the `--state-dir` backed up.
- Idempotent: re-running with no new source changes should apply zero new changes and log "nothing to do."
